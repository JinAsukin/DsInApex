## 1. 原始 P8 条目与判定

总计划里的 P8 共 5 条 + README §7.8 补充 4 条。逐条判定：

| # | 条目 | 可自动化 | 判定理由 |
|---|---|---|---|
| 1 | 8 个页面全量走查 | 🟡 **半自动** | 「路由 + 标题渲染 + 本地化绑定」可脚本化；「排版错位 / 控件重叠」不可 |
| 2 | 中英文切换全页面验证 | 🟢 **全自动** | 切语言后逐页比对控件真实文案，漏绑的控件会暴露为「两语言文案相同」 |
| 3 | 真实游戏实测（`audio_haptics_*`） | 🔴 **必须人工** | 需真实游戏 + 音频输出到虚拟 DualSense；无游戏时恒为 0 是设计使然（`RumbleBridge.cpp:34`） |
| 4 | 便携部署 / 迁移 / 清理流程验证 | 🟢 **全自动** | 解压、迁移、删除、残留检查全可脚本化 |
| 5 | 驱动管理向导完整走一遍 | 🟡 **半自动** | 检测部分已自动化；安装会改系统 + UAC，绝不能进自检 |
| 6 | 解压到含空格路径 | 🟢 **全自动** | 脚本直接用带空格路径跑 |
| 7 | 只读目录降级提示 | 🟢 **全自动** | 造只读目录跑，验 `AppDirectoryWritable=false` 且程序不崩 |
| 8 | U 盘部署 | 🔴 **人工** | 本机无 U 盘；但可验「非系统盘路径下引擎定位正常」，覆盖大部分逻辑 |
| 9 | 换目录后自启项纠偏 | 🟢 **全自动** | 迁移前后查注册表真源，验 `StalePath → Enabled` |
| 10 | 删除目录后残留检查 | 🟢 **全自动** | 删目录后查进程 / 注册表 / 引擎子进程 |
| 11 | 用户数据目录保留与清理说明 | 🟢 **全自动** | 删程序目录后确认 `%LOCALAPPDATA%\ApexSenseBridge` 仍在（预期在） |
| 12 | 全新环境首次驱动安装 → 重启 | 🔴 **无法复现** | 本机已装齐四个驱动，无法回到未装状态 |
| 13 | 托盘右键菜单实际弹出与点击 | 🔴 **必须人工** | 托盘菜单是 `ContextFlyout`，需真实右键；结构可查、弹出不可代 |
| 14 | 气泡通知视觉呈现 | 🔴 **必须人工** | 同上；且需肉眼确认视觉 |

**结论**：14 条里 **6 条全自动、3 条半自动、4 条必须人工、1 条无法复现**。
本阶段目标 = 把 6 条全自动 + 3 条半自动做到**有日志可复查**，并给 4 条人工项产出**逐步操作清单**。

## 2. 本阶段新增的工程产出

### 2.1 自检第 10 段：本地化覆盖审计（P8 新增）

**为什么要有这一段。** 原计划里「8 页面全量走查」和「中英文切换全页面验证」是人肉项。
但本项目最隐蔽的一类缺陷恰恰是**人眼很难发现的**：

> 某个控件漏绑 `loc:Localize.Key` → 中文界面下它显示的是 XAML 里写死的英文/占位文本，
> 界面整体看起来是通的，只是那一小块永远不翻译。

这类缺陷在 P6 踩过两次并写进了坑点清单（`Expander` 用 `Key` 会把整棵内容子树换成一行字符串；
`MenuFlyoutSubItem` 漏分支会变成空白项），**两次都是编译期毫无提示**。
既然已经踩了两次，就应该把它变成可自动检测的检查项，而不是继续靠人眼。

**审计两条腿：**

| 腿 | 检查内容 | 判据 |
|---|---|---|
| **A 静态（XAML 源码扫描）** | 全部 `.xaml` 里带 `loc:Localize.*` 的绑定，键是否在 `Strings` 两种语言里都存在 | 缺任一语言 → 报缺失 |
| **B 静态（漏绑检测）** | XAML 里**直接写死的可见文案**（`Text="..."` / `Content="..."` / `Header="..."`），且该控件没有 `loc:Localize.*` | 报「疑似漏绑」清单 |
| **C 动态（真实控件树）** | 逐页遍历，把每个已注册 `loc` 元素的**实际属性值**在中/英下各读一遍 | 键在 `Strings` 里查不到 → 报；两语言取值相同且键含 `Loc_` → 报可疑 |

⚠️ **B 腿必须容忍误报**：像 `Text="1920×1080"`、`Content="1"` 这类是数据不是文案。
判据设计为「**纯中文或纯英文单词、且长度 ≥ 2、且不是数字/单位/路径**」才报警，
宁可多报几条让人看，也不要漏掉真缺陷。

**C 腿是唯一能证明「本地化真的落到控件上」的检查** —— 与 P1 段的理由一致：
查字典永远返回正确值，只有读控件真实属性才能证明界面渲染对了。

### 2.2 `build/verify-p8.ps1`：端到端验收脚本

对标 `make-portable.ps1` 的风格（PS 5.1、UTF-8 with BOM、`√`/`×`、缺项 exit 1）。

**六个阶段，每阶段独立判定，任一阶段失败即 exit 1：**

| 阶段 | 内容 | 关键断言 |
|---|---|---|
| S1 布局基线 | 检查便携包 13 项布局 | 全在；且确认包是 build 产物（有 `App.xbf`） |
| S2 含空格路径 | 解压到 `...\P8 验收 空格 路径\...` 并跑自检 | 自检 10/10 段；`AppDirectoryWritable=true` |
| S3 迁移纠偏 | 登记自启 → 整目录改名 → 再启动 | 迁移后首跑 `StalePath` 被自动纠偏为 `Enabled` |
| S4 只读目录 | 去掉写权限后再跑 | `AppDirectoryWritable=false` 且**程序不崩、自检仍能跑完** |
| S5 清理残留 | 恢复权限 → 删除目录 | 进程为 0；`DsInApex` Run 值状态明确；引擎子进程为 0 |
| S6 数据保留 | 删目录后查用户数据目录 | `%LOCALAPPDATA%\ApexSenseBridge` **仍在**（便携语义：程序删了、用户数据留着） |

⚠️ **S3 的顺序有讲究**：必须**先启动一次**（让自启项被登记）→ 再搬目录 → 再启动（看纠偏）。
直接在未登记自启的情况下搬目录，`StalePath` 判定不成立（没登记就没有漂移）。

⚠️ **S4 只读目录会连带影响自检**：`ProbeWritable` 返回 false 是预期，但自检里
`p6Ok` 的判据若含 `AppDirectoryWritable` 就会误判失败。因此自检对只读目录
**只记录不判定** —— 这一点在实现时必须确认，不要想当然加进 `p6Ok`。

⚠️ **S5 删目录前必须先杀进程**：托盘驻留会锁 exe，导致删除失败并被误判成「删不掉」。

## 3. 不做的事（明确划界）

| 不做 | 原因 |
|---|---|
| 真实游戏实测的「代跑」 | 无游戏环境恒为 0，是引擎设计使然，跑了也只会得到假阴性 |
| 卸载驱动后重装 | 会破坏本机可用状态，且需要重启；本机是唯一开发环境 |
| 用 `dotnet publish` 产 P8 验收包 | P7 已定案：publish 会丢 XBF/PRI，产物启动即静默退出 |
| 把自启/驱动安装写进自检 | 自检的只读原则不能破（P6 起就明确） |
| U 盘实测 | 本机无 U 盘；用「非系统盘路径」部分覆盖并如实标注为未覆盖 |

## 4. 与 P9 的衔接

portable 交付下 Playnite 插件**不能**再靠注册表定位主程序（P7 报告已确认）。
本阶段 S2/S3 顺带产出一条可复用的经验：

正好验证了这条思路所需的健壮性。P9 直接复用本阶段的验收脚本做回归。

## 5. 验收尺子（唯一标准）

```
自动化：verify-p8.ps1 退出码 0
      + 自检日志 dsinapex_selftest.log 出现「自检结束：10/10 段通过」
      + 本地化审计零「疑似漏绑」

人工：  按 15-P8完成报告.md §人工项清单逐条签字
      + 真实游戏实测满足 SelfTest.VerifyBridgeLogSince 的全部必判项
```

**尺度说明**：本机无法复现「全新环境」，因此本阶段结论的适用范围是
**「本机环境下的端到端验收通过」**，不等于「任意新机器开箱即用」。
后者需在干净虚拟机或新装机器上补做，清单已在完成报告里写明。
