## 1. S4 补验：设备解析通过（并修掉一个真实 bug）

手柄插入并切 DInput 模式后，引擎 `list` 的真实输出：

```
Found 1 candidate(s):

[0] Flydigi VADER3
    VID:PID      0x04B4:0x2412
    Usage page   0xFFA0  usage 0x0001
    Reports      input=32 output=32 bytes
```
退出码 **0**，耗时 54–58 ms。

### 1.1 抓到的 bug：`0x` 前缀

**最初按纯文本推断写的正则是 `([0-9A-Fa-f]{4}):([0-9A-Fa-f]{4})`，实际输出带 `0x` 前缀，会静默失配**
——解析不报错，只是把所有字段留空。这正是"必须在真机取证才能发现"的典型问题。

修复后（两种形态都容忍，防上游改格式）：

```csharp
[GeneratedRegex(@"VID:PID\s+(?:0[xX])?([0-9A-Fa-f]{4}):(?:0[xX])?([0-9A-Fa-f]{4})")]
private static partial Regex VidPidRegex();
```

解析结果（控件实际值，非字典回读）：

```
✔ 解析出 1 个设备：
   [0] Flydigi VADER3
         VID:PID 04B4:2412　usage FFA0/0001　reports in=32 out=32
```

### 1.2 一个值得注意的产品细节

引擎把 APEX 4 报成 **`Flydigi VADER3`**——`VID_04B4` 是 Cypress 通用 VID，
多款飞智手柄共用该 HID 描述符。这意味着：

- **UI 上不能直接拿引擎返回的产品名当"APEX 4"展示**，否则用户会看到自己不认识的名字
- P2 的设备卡片需要做名称映射（或用 P4 驱动向导里的芯片识别逻辑矫正）

## 2. 障碍 A · `Trigger` → `VisualStateManager`（最高风险项）

### 2.1 改写规则（已实测确认）

| WPF | WinUI 3 |
|---|---|
| `<ControlTemplate.Triggers>` | `<VisualStateManager.VisualStateGroups>` 挂在模板根元素内 |
| `<Trigger Property="IsMouseOver" Value="True">` | `CommonStates` 组 → `PointerOver` 状态 |
| `<Trigger Property="IsPressed" Value="True">` | `CommonStates` 组 → `Pressed` 状态 |
| `<Trigger Property="IsEnabled" Value="False">` | `CommonStates` 组 → `Disabled` 状态 |
| `<Trigger Property="IsChecked" Value="True">` | `CheckStates` 组 → `Checked` 状态 |
| `<Trigger Property="IsSelected" Value="True">` | `SelectionStates` 组 → `Selected` 状态 |
| `<Setter TargetName="X" Property="Y" Value="V"/>` | `<Setter Target="X.Y" Value="V"/>` |
| `Value="{DynamicResource R}"` | `Value="{ThemeResource R}"` |

**易漏点**：
- 每个状态组要把所有状态都声明出来（哪怕空的 `<VisualState x:Name="Normal" />`），否则状态切换时不会复位
- **状态组声明顺序 = 优先级**，后声明的组覆盖先声明的

### 2.2 实测证据（读的是模板内元素的真实属性值）

以 `MainWindow.xaml` 上游 `ToggleSwitch` 模板（L15–48）1:1 改写为样板：

| 阶段 | `Track.Background` | `Thumb.HorizontalAlign` | `Thumb.Fill` |
|---|---|---|---|
| initial（未勾选） | `#FF2B2B2B` | `Left` | `#FF8A8A8A` |
| **checked** | **`#FF0070D1`** | **`Right`** | **`#FFFFFFFF`** |
| unchecked（切回） | `#FF2B2B2B` | `Left` | `#FF8A8A8A` |

**5 个 Setter 全部生效、状态可逆** → 改写方案成立。

### 2.3 剩余风险：`MultiTrigger` 的交叉状态（2 处）

上游有 1 处 `MultiTrigger`（GameListWindow.xaml:71）：

```xml
<MultiTrigger>
    <MultiTrigger.Conditions>
        <Condition Property="IsChecked" Value="False"/>
        <Condition Property="IsMouseOver" Value="True"/>
    </MultiTrigger.Conditions>
```

**"未选中 且 悬停"是交叉状态，VSM 的单维状态机表达不了。** 变通方案：

1. 多数情况下语义可近似为「`CheckStates/Unchecked` 下直接给目标值」（因为悬停时的差异本来就小）
2. 若确实需要区分，用 `CommonStates/PointerOver` + `CheckStates/Unchecked` 两个组各设一部分属性，
   靠**组顺序**控制覆盖关系
3. 极少数情况需在 code-behind 里手动 `VisualStateManager.GoToState`

**影响面小（仅 2 处），但改写时需逐个人工判断，不能机械替换。**

### 2.4 工期含义

36 处的改写模式已确定、样板已验证。**风险从"不知道能不能做"降级为"照着改就行"**。
建议 P1 的第一个任务就是把样板固化成规范，然后按 GameListWindow(23) → MainWindow(13) 的顺序推进。

## 3. 障碍 B · WindowsAppSDK 体积（结论：不裁剪）

### 3.1 两个方案实测均否决

| 方案 | 做法 | 结果 |
|---|---|---|
| **A** | 只引 `Microsoft.WindowsAppSDK.WinUI` + `.Runtime`，去掉元包 | ❌ **构建失败** |
| **B** | 保留元包，用 `ExcludeAssets="all"` 排除 AI/ML/Search/Widgets | ⚠️ **无效** |

**方案 A 的失败原因**（值得记住）：

```
error : The MSIX build tools use the 'CustomBeforeMicrosoftCommonTargets' MSBuild property
to wire up a custom .props file that sets some necessary properties.
This .props file does not appear to have been imported correctly.
```

> **`Microsoft.WindowsAppSDK` 元包不只是"聚合包"，它还承载 buildTransitive 的 MSBuild wiring。**
> 去掉它会导致导入链断裂。子包不能替代元包的构建职责。

日志里还有 `MSB4011: 无法再次导入 ... microsoft.windowsappsdk\1.6.250108002\buildTransitive\Microsoft.WinUI.props`
——说明有第三方包（H.NotifyIcon / WinUIEx）依赖 1.6 版元包，两套 targets 打架。

**方案 B 的失败原因**：

> 同一个子包被**两条路径**引入 —— 元包的依赖链 + 我们的显式引用。
> `ExcludeAssets` 只作用于显式声明的那条，元包那条照旧复制资产。

实测：236MB → 219MB（只减了 17MB，约等于排除掉的 `DirectML.dll`），
且 `onnxruntime.dll`、`Microsoft.ML.OnnxRuntime.dll` 仍在。

### 3.2 真相：体积大头不是 AI 组件

裁剪后 Top 体积文件：

```
Microsoft.Windows.SDK.NET.dll      ← SDK 投影
onnxruntime.dll
DirectML.dll
System.Private.CoreLib.dll         ← .NET 运行时
Microsoft.ui.xaml.dll              ← WinUI 本体
coreclr.dll                        ← .NET 运行时
Microsoft.WinUI.dll
Microsoft.UI.Xaml.Controls.dll
```

**这是 `SelfContained=true` + `WindowsAppSDKSelfContained=true` 的固有代价**，
不是"元包夹带私货"。AI/ML 组件合计仅约 22MB（约 9%）。

### 3.3 结论与后续建议

**不在构建期裁剪**（为 9% 冒运行时缺文件的风险不划算）。P7 打包阶段再决策：

| 选项 | 产物体积 | 代价 |
|---|---|---|
| 维持现状 + Inno **LZMA 压缩** | 安装包预计 **70–90MB** | 无（安装器本来就要压缩） |
| 改 **framework-dependent** | 应用目录 ~10MB | 用户需装 .NET 10 Desktop Runtime + Windows App Runtime，安装器要加这两个前置 |

> 本 Spike 的 236MB 是**未压缩的 Debug 产物**。Debug 配置不启用 R2R/裁剪，
> Release 配置会小一些。**用 236MB 判断"安装包会很大"是误判**——安装包大小取决于压缩后。

## 5. 本轮新增坑点汇总

| # | 坑点 | 详情 |
|---|---|---|
| 1 | **`list` 输出的 VID:PID 带 `0x` 前缀** | 纸面推断写正则会静默失配；必须容忍 `0x` / 无前缀两种形态 |
| 2 | **WinUI 3 的 `ControlTemplate` 没有 `FindName`** | WPF 有。模板内元素只能遍历可视化树拿（`VisualTreeHelper`） |
| 3 | **XAML 编译是两轮的，Pass1 失败会引发连锁误报** | 一个 C# 错误会让 Pass2 缺 `LocalAssembly`，进而让所有自定义附加属性报 `Unknown attachable member`。**排查时要先修根因，别被那一片红吓住** |
| 4 | **`Microsoft.WindowsAppSDK` 元包不能替换为子包** | 元包承载 buildTransitive wiring，子包替代会导致 MSIX targets 报 `CustomBeforeMicrosoftCommonTargets` 导入失败 |
| 5 | **`ExcludeAssets` 对付不了被多条路径引入的包** | 元包依赖链引入的那条不受显式引用的 `ExcludeAssets` 影响 |
| 6 | **引擎把 APEX 4 报成 `Flydigi VADER3`** | UI 不能直接展示引擎返回的产品名，需做名称映射 |
| 7 | **官方 WinUI 模板默认 packaged 且不锁版本** | 直接拿来用会带进 `Version="*"` 和 MSIX 工具链，必须改造 |
