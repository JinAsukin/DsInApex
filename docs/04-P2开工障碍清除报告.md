## 2. 障碍 2 · Toast 通知【已确认不可用】⚠️

### 2.1 实测结论

`AppNotificationManager.Default.Register()` 抛异常：

```
COMException: 找不到指定的模块。Unable to load resource dll.
Microsoft.WindowsAppRuntime.Insights.Resource.dll
```

### 2.2 根因（已追到源头）

| 追查步骤 | 结果 |
|---|---|
| 输出目录找该 DLL | ❌ 不存在 |
| NuGet 包里找 | ❌ **根本不在包里**，只有头文件 `WindowsAppRuntimeInsights.h` |
| 该 DLL 属于谁 | Windows App Runtime **安装包**的运行时资源 |
| 本机装了吗 | ✅ 装了（`Microsoft.WindowsAppRuntime.2` 2.5.1 等一堆） |
| 为什么还用不了 | **`SelfContained=true` 时不查系统安装的运行时**，只用自己的副本，而副本缺这个文件 |

### 2.3 这不是"代码写错了"，是部署模式的固有缺口

补两条旁证：
- **AUMID 其实是好的**：注册表 `HKCU\Software\Classes\AppUserModelId` 下已有系统按 exe 路径自动推导的项
  （`...win-x64.DsInApex.exe`，带 `NotificationGUID`）→ 问题不在身份，在资源文件
- **上游根本没用 Toast**：`ApexSenseBridgeTray/App.xaml.cs` 用的是
  `notifyIcon.ShowBalloonTip(...)`（WinForms 托盘气泡）

### 2.4 DIA 的方案：托盘气泡（与上游一致）

**托盘气泡走 `Shell_NotifyIcon(NIF_INFO)`，完全不依赖 WindowsAppRuntime 通知通道。**

| 维度 | Toast（AppNotificationManager） | 托盘气泡（Shell_NotifyIcon） |
|---|---|---|
| self-contained 可用性 | ❌ 不可用 | ✅ **可用** |
| 额外依赖 | Windows App Runtime 资源 DLL | **无** |
| 与上游一致性 | 上游没用 | ✅ 上游正是这么做的 |
| 需要托盘图标 | 否 | 是（DIA 本来就有） |
| 视觉形态 | 通知中心 + 横幅 | 托盘区气泡 |

### 2.5 对 P2 的实际影响：**零**

因为 **P2 的"通知开关"只是一个设置项**（存布尔值到 `tray_settings.json`），
真正发通知是 P6 的事（桥接激活 / 游戏识别 / 更新可用）。

`NotificationService` 已改造为：
- 保留 Toast 通道实现，但**明确标注为不可用**，并提供 `IsToastAvailable`
- `Diagnose()` 输出可核查的状态，把「不可用」写成**预期结论而非 bug**
  （避免未来有人看到这条又去查一遍）
- 托盘气泡通道留到 P6 接托盘时实现（需要 `TaskbarIcon` 实例）

> **给未来的自己**：如果哪天真要 Toast，唯一出路是把部署模式改成
> framework-dependent（让应用去用系统装的 Windows App Runtime）。
> 但那会要求用户额外装运行库 —— 与"接上就能用"的产品目标冲突，不划算。

## 3. 障碍 3 · 托盘与 NavigationView 共存 ✅

P1 的导航壳是 `TitleBar + NavigationView` 双层布局，而托盘 `TaskbarIcon` 也要往窗口里挂。
实测结果：

```
托盘图标 IsCreated = True
右键菜单项数       = 5
```

独立佐证（注册表）：`HKCU\Control Panel\NotifyIconSettings` 下同时存在
Spike 与 P1 两个 exe 的托盘图标记录。

**关键实现细节**：
- `TaskbarIcon` 放在根 `Grid` 里、`RowDefinitions` **之后**（无可视内容，不影响布局）
- 菜单走 `FrameworkElement.ContextFlyout`（H.NotifyIcon 2.4.1 无 `ContextMenu` 属性）
- 菜单项文案用 `loc:Localize.Key`，**托盘菜单也跟着语言热切换**

## 4. 障碍 4 · 关闭窗口驻留托盘 ✅

```csharp
AppWindow.Closing += OnAppWindowClosing;

private void OnAppWindowClosing(AppWindow sender, AppWindowClosingEventArgs args)
{
    args.Cancel = true;   // 拦截关闭
    sender.Hide();        // 隐藏到托盘
}
```

理由：桥接需要在后台持续工作，点 X 不该把服务一起带走。
退出走托盘菜单的"退出"。

> ⚠️ **副作用提醒（开发期）**：这个行为会让进程常驻，重新构建时会因
> `DsInApex.exe` 被占用而报 `MSB3027 / MSB3021`。
> 开发时用 `taskkill /IM DsInApex.exe /F` 先停掉。

## 5. 本轮新增坑点

### 坑 14 · XAML 属性元素必须在子元素之前

- **现象**：`WMC0035: Duplication assignment to the 'Children' property of the 'Grid' object`
- **根因**：把 `<Grid.RowDefinitions>` 写在了 `<TaskbarIcon>` **之后**。
  XAML 规定属性元素（`xxx.RowDefinitions` 这类）必须出现在内容子元素之前
- **解法**：属性元素前置
- **备注**：这条与 WPF 一致，属基本功疏忽，不是 WinUI 3 特有问题

### 坑 15 · self-contained 部署会缺 WindowsAppRuntime 的运行时资源

见 §2.2。**推论**：以后凡是用到 WindowsAppSDK 里"需要运行时资源"的功能
（通知、AI 组件等），在 self-contained 下都要先实测一遍，别假设它可用。

### 坑 16 · `AppNotificationManager` 没有 `GetCurrentAumid()` API

- **现象**：`CS1061: "AppNotificationManager"未包含"GetCurrentAumid"的定义`
- **根因**：WindowsAppSDK 没有托管 API 读 AUMID
- **解法**：P/Invoke `shell32!GetCurrentProcessExplicitAppUserModelID`
- **附带收获**：unpackaged 应用若没显式设过 AUMID，此 API 会返回失败 ——
  而**注册表里仍会有系统按 exe 推导的项**，两者不矛盾
