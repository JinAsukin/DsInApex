### 1.1 `build/make-portable.ps1`（473 行）

一步完成：构建 → 目录规范组装 → 写入 `version.json` → 生成 `SHA256SUMS.txt` → 压 ZIP → 打印 13 项布局自检。

| 参数 | 作用 |
|---|---|
| `-Configuration` / `-Platform` | 默认 `Release` / `x64`（**`Platform` 必须显式指定**） |
| `-Version` | 覆盖版本号；默认从 csproj `<Version>` 读 |

| `-KeepEngineDrivers` | 保留 `engine\Drivers\`（默认剔除，见 §2.2） |
| `-NoZip` | 只组装目录 |

脚本内含两道**硬闸门**（不通过就抛错退出，绝不产出废包）：

1. **XAML 完整性闸门** —— `DsInApex.exe` / `DsInApex.pri` / `App.xbf` / `MainWindow.xbf` 四者缺一即报错，
   并直接提示「高度怀疑你用的是 `dotnet publish` 产物」。
2. **版本一致性校验** —— 比对 exe 的 `ProductVersion` 与打包版本号，不一致就告警。

## 2. 体积账（268 MB → 214 MB）

### 2.1 明细

| 动作 | 省下 | 说明 |
|---|---|---|
| 剔除 WindowsAppSDK 元包夹带的 **AI / ML / Search / Widgets** 子系统 | **≈ 54 MB** | `onnxruntime.dll` 20.7 + `DirectML.dll` 17.8 + `Asg.SemanticIndex` 3.8 + `Windows.Search` 3.5 + `Widgets` 2.6 + WebView2 部分 |
| 关闭 Release 调试符号（`.pdb`） | < 1 MB | App 与 Core 两个项目都要设，漏一个仍会带出来 |
| 交付改用 `dotnet build` 而非 `publish` | — | publish 产物反而**不完整**（§3.1） |
| 剔除 `engine\Drivers\`（与 `Prerequisites\` 重复） | 34 MB（解压） | 同一批安装器两份拷贝 |
| 剔除引擎内上游 Tray / Control / 启动脚本 | 0.9 MB | DIA 已用 WinUI 3 全量替代，留着只会让用户不知道点哪个 |

**终值**：解压 **228.9 MB** / **507 文件** → ZIP **104.7 MB**（压缩率 45.7%）。

> 对比：README §5.7 原本预计「Inno Setup LZMA 能压到 70–90 MB」。
> 实际 portable 包 104.7 MB —— 差额主要是包内多了引擎（16 MB）与两个驱动安装器（33 MB，
> Inno 时代同样要带），所以这个数字是合理的。

### 2.2 关于剔除 `engine\Drivers\`

上游 `README-PORTABLE.txt` 写着「Keep every EXE and DLL, plus the Resources, Data, **Drivers**, and Licenses folders together」。
但那是给**上游托盘版**的 `Install-Drivers.cmd` 用的：
grep 上游 C++ 源码，**没有任何代码引用 `Drivers\` 目录或那两个安装器文件名**。
DIA 的驱动安装走自己的 `Prerequisites\` + `DriverInstallerService`，两处是同一批文件。
→ 默认剔除，`-KeepEngineDrivers` 可保留。**已实测**：剔除后引擎定位、部署自检、9 段自检全部正常。

## 3. 本轮踩到的坑（**最高价值部分**）

### 3.1 🔴 `dotnet publish` 产出的是**启动即死**的包（本轮最大的坑）

第一次打包用的是教科书写法：

```powershell
dotnet publish src\DsInApex.App -c Release -r win-x64 --self-contained true -o out
```

产出 539 个文件、268 MB，看着比 `build` 输出还完整。结果：

```
$ ./DsInApex.exe        → exit code 127，零日志、零输出、无窗口
```

`DsInApex.exe` 文件确实存在、权限正常、双击也没反应 —— 典型的「进程启动即退出」。
把**可运行的 Debug 目录**与 publish 目录做文件名差集，一眼看出问题：

```
< ./App.xbf            ← XAML 编译产物，缺
< ./MainWindow.xbf
< ./Views/*.xbf        ← 8 个页面全缺
< ./DsInApex.pri       ← 资源索引（PRI），缺
< ./Assets/*           ← 图标与图片，缺
```

**WinUI 3 + Unpackaged + SelfContained 组合下，`dotnet publish` 不会复制 XAML 编译产物。**
而 `dotnet build` 的输出目录**本来就是完整的可运行集合**（self-contained 运行时在 build 阶段
就已复制到输出）。→ **交付物定案：取自 `dotnet build` 输出，永不使用 publish。**

> 这个坑的危险之处在于「静默」：文件数看着更多、体积看着更小、构建退出码 0、
> 没有任何一条 error/warning。只有真的双击一下才知道。

### 3.2 🔴 WindowsAppSDK 元包夹带了一整套 AI 运行时（54 MB）

`dotnet list package --include-transitive` 才看得见的传递依赖：

```
Microsoft.WindowsAppSDK.AI              2.5.5
Microsoft.WindowsAppSDK.ML              2.1.94
Microsoft.Windows.AI.MachineLearning    2.1.74
Microsoft.WindowsAppSDK.Search          2.5.5
Microsoft.WindowsAppSDK.Widgets         2.0.5
```

self-contained 部署会把它们的原生库一并复制进产物 —— 其中 `onnxruntime.dll`（20.7 MB）
与 `DirectML.dll`（17.8 MB）纯属给 Windows AI / 语义索引用的，DIA 一行都不碰。

**解法**：显式引用该子包 + `ExcludeAssets="all"`（版本号必须与传递解析出的版本**逐字一致**）。

> ⚠️ **与 README §5.7 的旧结论不冲突，别互相类推**：
> 元包 `Microsoft.WindowsAppSDK` **本身**不能用 `ExcludeAssets` 去掉（它承载 buildTransitive
> 的 MSBuild wiring，去掉后 MSIX targets 直接报错）；但**子包**可以。
> 两者机制不同，这是本轮新增的一条分辨规则。

### 3.3 `build\` 被 gitignore 整个忽略 —— 连打包脚本一起

`.gitignore` 里原有 `/build/`（源自 C++/CMake 构建输出的习惯）。
P7 把 `make-portable.ps1` 放在 `build\` 下 → **脚本会静默不入库**，别人 clone 下来根本没有打包能力。

→ 改成 `/build/*` + `!/build/*.ps1`。验证方法：`git status -uall build/` 必须能看到脚本。

### 3.4 PowerShell 5.1 的两条编码规则

| 现象 | 原因 | 处理 |
|---|---|---|
| 脚本里的中文注释/输出变乱码 | PS 5.1 读**无 BOM** 的 UTF-8 脚本时按 ANSI（GBK）解析 | 脚本必须存 **UTF-8 with BOM** |
| 脚本里 `✓` `✗` 显示成 `?` | 这两个码位**不在 GBK 字符集**里，`Write-Host` 走控制台代码页 | 改用 `√` `×`（GBK 内含） |
| `dotnet build` 的中文输出变乱码 | dotnet CLI 输出 UTF-8，PS 5.1 按 936 解码 | 脚本开头 `[Console]::OutputEncoding = UTF8` |

### 3.5 远端仓库与本地是**两段无关历史**

`JinAsukin/DsInApex` 早在 P3 就建了仓（只放 `data/supported_games.json` 作云端数据源，
README 写着「应用源码将在首次发布后发布到这里」）。本地仓库这时的 HEAD 停在 P2 预备，
而 P3–P7 的全部代码**从未提交过**（93 个跟踪文件 vs 89 个待提交改动）。

发布时必然撞上两件事：

1. **本地没有 `remote`** —— 需要 `git remote add origin`；
2. **两段历史无关** —— 直接 push 会被拒。

处理：`git merge origin/main --allow-unrelated-histories`，唯一冲突是 `README.md`（两边都有）；
取本地的新 README，并**把远端 README 里的「数据源」信息并入新 README**（不丢内容）。
合并后核对 `data/supported_games.json` 与嵌入副本 `Core\Data\supported_games.json` 的 MD5 —— **一致**。

> 教训：**「仓库已存在」不等于「你推得上去」。** 推送前先 `gh repo view` + `git ls-remote` 侦察远端。

### 3.6 合规复核抓出 3 个真实缺口

| # | 缺口 | 处理 |
|---|---|---|
| 1 | **`LICENSE` 不是完整 GPL 文本**，只是声明摘要 —— 却写着「完整文本见 LICENSE」（自相矛盾）。GPL-3.0 §4 要求**随作品提供许可证副本**，给 URL 不算 | 换成 GNU 官方全文（674 行，gnu.org 直连可取），声明与修改说明移入新文件 `NOTICE.md` |
| 2 | **usbip-win2 许可证记载矛盾**：`THIRD_PARTY_NOTICES.md` 上游段落写 `BSD-2-Clause`，DIA 增补段落写 `GPL-2.0`；而安装器**随附的** `USBIP-WIN2-LICENSE.txt` 是 **BSD-2-Clause** | 以**随附许可文本**为准，两处统一为 BSD-2-Clause，并注明内核驱动组件以安装器内声明为准 |
| 3 | `SOURCE_OFFER.md` 写「设置与**书籍记录**」 —— 从别的项目抄来的措辞，本项目是**学习记录** | 修正 |

另外顺带：`SOURCE_OFFER.md` 的构建命令缺 `-p:Platform=x64`，与 README 不一致 → 统一。
