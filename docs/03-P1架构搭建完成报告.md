## 4. 本轮新增坑点

### 坑 10 · WinUI 3 内置控件里没有 `HeaderedContentControl`

- **现象**：`CS0246: 未能找到类型或命名空间名"HeaderedContentControl"`
- **根因**：`HeaderedContentControl` 是 **CommunityToolkit** 的控件，不在 WinUI 3 内置集里。
  内置的带 Header 控件只有 `Expander`
- **解法**：`Header` 路由改为直接匹配 `Expander`

### 坑 11 · `Expander` 继承自 `ContentControl`，switch 模式顺序敏感

- **现象**：`CS8510: 该模式不可访问。它已由 switch 表达式的前一个 arm 处理`
- **根因**：`Expander` 是 `ContentControl` 的子类。若 `case ContentControl` 写在前面，
  后面的 `case Expander` 永远匹配不到，编译器直接报错
- **解法**：**子类分支必须排在父类之前**

### 坑 12 · XAML 编译连锁误报（第二次踩到，已形成排查套路）

- **现象**：一个 C# 编译错误，会引发**几十条** `Unknown attachable member 'Localize.Key'`
- **根因**：XAML 编译分 MarkupCompilePass1 / Pass2 两轮。Pass1 因 C# 错误失败后，
  Pass2 缺 `LocalAssembly` 参数（日志里有 `WMC1509` 警告），导致 XAML 编译器
  无法解析本项目内的类型（含所有自定义附加属性）
- **排查套路**（重要）：
  1. 先在错误列表里**找 `error CS` 开头的行** —— 那是根因
  2. 撇开所有 `WMC0010` 附加属性报错不看
  3. 修掉唯一的 CS 错误，重新构建，那一大片红会自动消失
  **别去查附加属性本身**，它没坏

### 坑 13 · 日志文件 UTF-8 无 BOM，用默认编码读会乱码

- **现象**：`Get-Content` 读出 `[INFO] DI 瀹瑰櫒宸叉瀯寤?`
- **根因**：`AppLog` 写的是 UTF-8 **无 BOM**（与上游一致），
  而 Windows PowerShell 5.1 的 `Get-Content` 默认按系统 ANSI（GBK）解码
- **解法**：读取时显式指定 —— `Get-Content $log -Encoding UTF8`
- **取舍说明**：刻意保持无 BOM 以与上游 `AppLog` 行为一致（P8 验收工具链依赖该格式），
  **不**为了读取方便改文件格式
