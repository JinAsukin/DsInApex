## 1. 起因：issue #26 与上游回复

我们提交的 issue：
[`[Bug] Apex 4 exposes two USB identities with identical VID:PID - RT adaptive triggers silently inactive in the degraded one`](https://github.com/ReynArts/ApexSenseBridge/issues/26)（OPEN，作者 JinAsukin）

上游维护者 ReynArts 的回复（2026-10-04）要点：

1. **同一 `04B4:2412` 会暴露两种接口**：完整 64 字节 APEX 4 扳机接口 / 降级 32 字节 `VADER3` 式接口；
2. 降级身份上 **HID 写入会成功，但固件路径没实现 RT** —— 这就是"写不报错但扳机没反应"的假阳性根源；
3. 已准备修复：把两种接口分类，`identify` 把 32 字节态报成 `partial`，桥接启动时提示重新接入；
4. **刻意不阻断全部输出**，因为降级态下 LT 与震动仍有价值；
5. 身份切换是**手柄/固件行为，ASB 无法安全修复**；
6. 请求：新版构建出来后，**在两种状态下各跑一次 `ApexSenseBridge.exe identify` 并粘贴输出**。

→ 关键判定：回复里说的"next test build"就是当天（2026-10-04T16:02）发布的 **v1.0.0-beta.10**。
所以本轮的入口是"升级引擎"，而不是"自己实现一个识别"。

## 3. 三项修复的适配

### 3.1 #26 降级身份三态 → 我们的解析器与界面

**问题**：我们的正则原本是 `^Adaptive triggers:\s*(yes|no)`。
新引擎的 `partial (...)` **匹配不到** → 被静默判成"不支持"，
把语义从"LT 仍可用、只是 RT 不行"错译成"整支手柄没有自适应扳机"。
这是与 #26 **同构的镜像缺陷**：上游误报成 `yes`，我们会误报成"全无"。

**改动**：

| 文件 | 改动 |
|---|---|
| `Core/Models/EngineReports.cs` | 新增 `ApexTriggerCapability { Unknown, Full, Partial, None }`；`AdaptiveTriggers` 改为**派生**属性且**仅 Full 为 true**；新增 `AdaptiveTriggerAction`（引擎 `Action:` 行原文） |
| `Core/Services/EngineOutputParser.Reports.cs` | 正则吞掉整行后按**前缀**分类（`partial`/`yes`/`no`），并解析 `Action:` 行；无法识别才回落 `Unknown`（保持"未声明"语义，不臆断） |
| `App/ViewModels/HardwareTestViewModel.cs` | 硬件页「设备身份」新增三态文案 + 原样带出处置建议行 |
| `Core/Localization/Strings.cs` | 新增 `Loc_HwAdaptiveFull/Partial/Unknown`、`Loc_HwField_Action`（双语） |

**新增自检段（关键）**：`MainWindow.CheckAdaptiveTriggerContract()` ——
用**四条实测原文**的合成样本把"原文 → 三态"钉死，纯字符串、无副作用、不要求手柄在位：

```
√ 原文「yes (full 64-byte Apex 4 interface)」→ Full（期望 Full）
√ 原文「partial (degraded 32-byte Apex 4 interface; LT may work, RT unavailable)」→ Partial（期望 Partial）
√ 原文「no」→ None（期望 None）
√ 原文「yes」→ Full（期望 Full）        ← 兼容 beta.9 的老格式
√ 降级样本带出 Action: 处置建议
√ AdaptiveTriggers 只对完整接口为 true（Partial 必须为 false）
```

该断言已并入 P5 段判定 → 引擎哪天再改这行文字，自检立刻红。

**真机端到端验证**（本机 APEX 4 / 固件 0x6837 / 当前降级态）：

```
identify 退出码=0 机型=Apex 4 固件=0x6837 连接=Dongle 扳机=Partial 处置建议=有
三态契约 = 通过
```

### 3.2 #15 启动超时后的子进程回收 → 我们**同款缺陷**

**问题**：上游修的是"启动超时后，启动器丢弃了唯一句柄，而那个不响应 Stop 事件的孤儿引擎进程
继续持有全局会话锁 `Local\ApexSenseBridge.ActiveSession.Owner.v1`，
导致之后每次启动都被判成'已有外部会话'"。

**我们的 `BridgeSession` 是完全一样的写法**：

```csharp
if (!session.WaitUntilReady(timeout, out error))
{
    session.StopAndWait(DefaultStopTimeout);   // ← 停不下来就直接 Dispose 句柄
    session.Dispose();
    return null;
}
```

即：如果引擎不响应 Stop 事件，我们会留下一个**持有会话锁的孤儿进程**，
用户看到的现象是"手柄突然再也启动不了桥接，重启 DIA 也没用"。

**改动**（主程序与插件两侧同步）：

| 文件 | 改动 |
|---|---|
| `Core/Services/BridgeSession.cs` | 新增 `StopAndEnsureExit(cooperative, forced)`（作用域严格限定**本次启动的那一个进程**，不按名字扫全系统）；新增 `CooperativeStopOnFailure=3s` / `ForcedStopOnFailure=5s`；异常清理路径新增 `KillQuietly`（先杀再放句柄） |
| `Core/Services/EngineSessionManager.cs` | 正常停止改走 `StopAndEnsureExit(15s, 5s)`，非干净退出时写日志留痕 |
| `Playnite/BridgeSession.cs` | 同上（含 3s/5s 常量与 `KillQuietly`） |
| `Playnite/DsInApexPlugin.cs` | 停止路径改走 `StopAndEnsureExit` |

> 为什么启动失败路径只给 3 秒：这条路径上引擎**从未报告过 Ready**，
> 不存在"需要时间把手柄从虚拟态还原"的前提；等满 15 秒只会让
> "点启动 → 卡 15 秒 → 失败"的体感更糟。上游用的也是这一对量级。
> 正常停止路径仍是 15 秒不变（`apex_original_restored` 依赖这段等待）。

### 3.3 #10 APEX 4 陀螺仪灵敏度 → 新能力接入

上游实测结论是"三轴在游戏里都有数据但偏弱，尤其 yaw"，于是给出**有界全局增益**
（`--apex4-gyro-strength 25..400`、`--apex4-gyro-yaw-strength 25..400`，100 = 引擎原始标定），
并**明确不伪称拿到了出厂标定**。

我们把它接进了设置页（主程序 + 插件两侧）：

| 文件 | 改动 |
|---|---|
| `Core/Models/TraySettings.cs` | `Apex4GyroStrengthPercent` / `Apex4GyroYawStrengthPercent`（默认 100） |
| `Core/Services/EngineSessionManager.cs` | `BuildArguments` 追加两个参数（**仅在非默认值时**）+ `ClampGyroPercent` + 公开常量 `GyroPercentMin/Max` |
| `App/ViewModels/SettingsViewModel.cs` | 两个 `NumberBox` 绑定属性 + `ResetApex4GyroCommand` + 状态行文案 |
| `App/Views/SettingsPage.xaml` | 新增「APEX 4 陀螺仪」Expander（双档位 + 恢复默认） |
| `Playnite/*` | 插件设置项、设置视图两行、参数拼装、`VerifySettings` 区间校验、双语键 |

🔴 **两处夹紧，不是一处**：25–400 是引擎硬边界，越界**不是被忽略而是拒绝启动**。
所以 `NumberBox` 的 `Minimum/Maximum` 只是第一道闸，
`tray_settings.json` 是用户可手改的，必须在拼参数时再夹一次（两处都做了）。

> 也顺手去掉了 `make-portable.ps1` 里写死的「（首个便携版）」字样 —— 它对 0.7.1 起就已是错的。

## 4. 副产物：修掉一个长期误报的本地化审计假阳性

**现象**：跑自检时 P8 本地化覆盖率一致判「控件树腿未通过」，报
`不支持的控件类型 = 138 条（真缺陷）`，明细全是
`✗ [TextBlock] Loc_NavDiagnostics → 诊断 / (英文采样缺失)`。

**定性过程（没有靠猜）**：`git stash` 掉本轮全部改动 → 重建 → 跑自检 →
**同样 9/10、同样 138 条**。说明**与本轮改动无关**，是既有缺陷。

**根因**：审计腿的中文/英文采样是**两次独立的弱引用快照**，然后按 `(键, 控件类型)` 配对：

```csharp
var zhSamples = Localize.SampleApplied();   // 快照 A（弱引用）
LocalizationService.Shared.SetLanguage(Langs.En);  // ← 触发 RefreshAll，会清理已回收条目
var enSamples = Localize.SampleApplied();   // 快照 B
// 配对失败 → "(英文采样缺失)" → 被 sentinel 判成"控件类型不支持"
```

注册表存的是**弱引用**，`SetLanguage` 又会触发 `RefreshAll` 清理已回收条目。
只要两次采样之间发生一次 GC，英文侧就少掉一批元素 → 大面积假阳性。
**这条腿本身是 flaky 的**：P8 报告（2026-10-03）当次记录是 `0 条`（走运），本轮两次复现都是 138/152 条。

> 危害不只是"误报"：它报的"真缺陷"里绝大多数是它自己制造的，
> 会把人训练成**忽略这条检查** —— 那比没有检查更糟。

**修法**：改为**一次快照拿到强引用目标集合 + 中文取值**，切语言后对**同一批目标**逐条读英文取值。
两次读值的目标集合恒等 → 配对逻辑彻底消失 → 不存在"缺失"。

| 文件 | 改动 |
|---|---|
| `App/Localization/Localize.cs` | 新增 `AppliedTarget` 记录 + `SnapshotTargets()`（强引用，顺手清死条目） |
| `App/MainWindow.xaml.cs` | 控件树腿改为「快照 → 切语言 → 同一批目标读值」 |

**结果**：`不支持的控件类型 = 0 条`、`字典缺键 = 0 条`、`双语同文 = 0 条`、**自检 10/10 段**。

> 顺带记录一个**审计盲区**：走 `{x:Bind}` 的 VM 计算属性**不在** `loc` 附加属性注册表里，
> 控件树腿扫不到它们。所以本轮新增的 `Apex4GyroStateText` 必须手动加进
> `SettingsViewModel.RaiseLocalizedTexts()`（否则切英文后这一块会停在中文）。
> 该函数已补注释说明这条规矩。

## 5. 顺手消除的两个"易漏点"

### 5.1 `EngineLocator` 的硬编码版本目录（第 3 处要改的地方）

换引擎原本要改**四处**，而记忆里只记着三处：

1. `make-portable.ps1` 的 `$EngineSource`（引擎源目录）
2. `make-portable.ps1` 的 `$EngineVer` / `$EngineBase`
3. **`EngineLocator.cs` 的 `vendor\portable-<版本>\...`**（开发期引擎发现）

本轮实测踩到：`vendor/` 下 beta.9 与 beta.10 并存时，开发期自检仍会命中**旧版**，
表现是"新引擎的修复本地复现不出来"。

**修法**：改为扫描 `vendor\portable-*\ApexSenseBridge-Portable\` 并按**版本降序**取第一个存在的
（数字段逐位比较 → 正式版优于预发布 → 预发布序号大者优 → 标签字典序兜底）。
排序完全确定，不再依赖文件系统返回顺序，**新增引擎只需把包放进来**。

### 5.2 打包脚本新增「引擎版本守门」

`make-portable.ps1` 复制完引擎后，**执行包内 `engine\ApexSenseBridge.exe help`**，
从 `Release:` 行取真实版本与 `$EngineVer` 比对，不一致**直接 throw**：

```
[OK]   引擎版本守门通过：包内 ApexSenseBridge.exe 自报 1.0.0-beta.10
```

这条守门正是为了防住 0.7.1 真实踩过的坑：只改源目录不改版本号时，
`version.json` 声明的引擎与实际打包进去的二进制不符，而**编译/打包全绿、零提示**。
