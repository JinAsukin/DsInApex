## 4. 本轮三条关键认知（**会影响 P8 验收，务必记住**）

### 4.1 音频触觉的输入源是「游戏 → 虚拟 DS5」，不是系统音频回环

`audio_haptics_processed` 的累加点在 `src/dualsense/RumbleBridge.cpp:34`：

```cpp
if (feedback.kind == FeedbackKind::AudioHaptics) {
    audioFrames_.fetch_add(1, std::memory_order_relaxed);
```

这个 `feedback` 来自 **游戏写往虚拟 DualSense 的输出报告**。推论：

- 没游戏时 `audio_haptics_processed` **恒为 0**
- **在扬声器上放音乐/闹钟不会让它变正** ← 本轮一开始就按"回环"假设去放音频，实测无效，白跑一轮
- 因此 P8 的 `audio_haptics_active_percent > 0` **只能在真实游戏里复现**

### 4.2 `last_active_*_ds_type` 同理需要游戏力反馈指令

无游戏 → `last_active_lt_ds_type=0`、`last_active_lt_apex=none`。
这不是"扳机没工作"，而是"没人给扳机发过指令"。

### 4.3 `tray_bridge.log` 是**托盘侧**写的，不是引擎写的

- 引擎只往 **stdout** 吐诊断指标
- 是上游 `ApexSenseBridgeTray/App.xaml.cs:179` 订阅 `sessionManager.LogMessage` 再 `AppLog.WriteLine("tray_bridge.log", msg)`
- **DIA 一开始漏了这根接线** → 会话明明成功，`tray_bridge.log` 却一个字节没涨（首轮联调就卡在这）
- 已补在 `AppHost.Build()`：`session.LogMessage += msg => AppLog.WriteLine("tray_bridge.log", msg)`
- ⚠️ **文件名与目录必须与上游一致**，否则 P8 验收脚本读不到指标

> **给未来的自己**：日志相关的"接线"在迁移时最容易漏 —— 因为 `EngineSessionManager`
> 只负责抛事件，**谁订阅、写去哪，是 App 层的决定**。上游把这个决定放在 `App.xaml.cs`。
> 以后凡是迁"抛事件的服务"，都要回去看一眼上游**谁订阅了它**。

## 5. 本轮新增坑点

### 坑 17 · 迁移"抛事件的服务"时，事件订阅方也会丢

见 §4.3。`EngineSessionManager` 本身照搬无误，但它的**消费者**（日志接线、托盘状态更新、
通知）都在上游 App 层，重写 UI 时不会自动带过来。**清单式核对法**：
迁完一个服务，回去 `grep 服务名` 在上游 App 层出现的位置，逐个确认 DIA 侧是否等价实现。

### 坑 18 · `StopAndWait` 之后进程虽退出，管道里的最后几行可能还没读完

`Process.WaitForExit(ms)` 只等进程退出，**不等异步输出回调排空**。
被丢掉的往往正是最后写入的验收指标（`apex_original_restored` 恰恰在末尾）。

**解法**：进程退出后再调一次**无参重载** `process.WaitForExit()` —— 它会等输出流读完。

```csharp
bool exited = process.WaitForExit((int)timeout.TotalMilliseconds);
if (exited) process.WaitForExit();   // 等异步输出回调排空
```

上游没有这一步（属上游的潜在丢日志问题），DIA 补上。**这是 DIA 侧主动改进，不违反"引擎保持上游原样"**
（该约束只针对 C++ 引擎层）。

### 坑 19 · 托盘 `TaskbarIcon.ToolTipText` 不吃 `loc:Localize.Key`

`Localize` 的 ToolTip 路由写的是 `ToolTipService.SetToolTip`，而 `TaskbarIcon.ToolTipText`
是它自己的属性。**必须手工设**，且在语言变更 + 会话状态变更两处都要刷。

### 坑 20 · 再次撞上"驻留托盘导致 exe/dll 被锁"

`MSB3027 / MSB3021: 文件被 DsInApex 锁定`。
自检跑完进程仍驻留托盘 → 下一次构建必失败。**先 `taskkill //IM DsInApex.exe //F`**。
（README §5.7 已记，本轮又踩一次 —— 说明它是高频动作，不是偶发。）

## 8. 复现命令

```bash
# ── 构建（务必在代码区，且先清驻留进程） ──
cd /e/DsInApex
taskkill //IM DsInApex.exe //F
dotnet build DsInApex.sln -c Debug

# ── 常规自检（不碰手柄） ──
DIA_SELFTEST=1 ./src/DsInApex.App/bin/x64/Debug/net10.0-windows10.0.26100.0/win-x64/DsInApex.exe
# 结果：C:\Users\Asukin\AppData\Local\ApexSenseBridge\logs\dsinapex_selftest.log
# 读取必须指定编码：Get-Content $log -Encoding UTF8

# ── 真机会话冒烟（★ 会真实接管手柄，需手柄在 DInput 模式在位） ──
DIA_SELFTEST=1 DIA_SESSION_SMOKE=1 ./DsInApex.exe
# 另看：%LOCALAPPDATA%\ApexSenseBridge\logs\tray_bridge.log
```

**环境变量开关总表**

| 变量 | 作用 |
|---|---|
| `DIA_SELFTEST=1` | 启动时执行 6 段验收自检并写日志 |
| `DIA_SESSION_SMOKE=1` | **与上面同时设置**才生效：真实起停一次桥接会话（接管手柄） |
| `DSINAPEX_ENGINE_PATH` | 覆盖引擎路径（文件或目录均可） |
