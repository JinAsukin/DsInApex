## 3. 本轮踩到的坑（均已修复）

### 3.1 🔴 `Expander` 用 `loc:Localize.Key` 会把整棵内容子树换成字符串

`Expander` 继承自 `ContentControl`，而 `Localize.ApplyAuto` 的类型分派里
**没有 `Expander` 分支** → 命中 `case ContentControl` → `cc.Content = text`。

后果：`<Expander loc:Localize.Key="...">` 里的那个 `ScrollViewer` 会被**整个替换成一行文字**，
而且编译期毫无提示。

**修法**：`Expander` 必须用 `loc:Localize.Header`（它的标题才叫 Header）。

> 教训：这个附加属性的"智能路由"是双刃剑 —— 它对未知的 `ContentControl` 子类会
> 乐观地认为"文案应该放 Content"。**给没见过的控件加 `loc:Localize.Key` 之前，
> 先确认它的正文属性叫什么。**

### 3.2 🔴 `input-status` 首次调用会因设备占用失败（不是 bug，是环境）

实测现象：同一条命令，**首跑退出码 2**：

```
APEX identity verification failed: No valid command 0xEC Apex 4 identity reply arrived
after 30 attempts; ... close Flydigi Space Station before retrying
```

间隔约 1 秒后重试即成功（1001 份报文、0 超时）。当时 `SpaceStationService` 正在运行。

**修法（分两类处理）**：

| 命令类型 | 策略 |
|---|---|
| 只读命令 | 遇退出码 2 **自动重试一次**（间隔 1.2 秒），并在结论里标注"含重试" |
| 写硬件命令 | **绝不重试** —— 用户不能因为一次自动重试感到两次扳机 / 震动 |

**推论**：`SpaceStationService` 是这类"读不到设备"故障的头号嫌疑，
这也是诊断页把冲突进程检测放在第 5 步的原因。

### 3.3 🔴 机型判定不能依赖产品名（APEX 4 报的是 `Flydigi VADER3`）

第一版冒烟得到 `机型判定 = inconclusive`，警告"没有任何接口报出 APEX 4 机型名称"。

**根因**：APEX 4 的四个 HID 接口**全都沿用旧版固件的产品字符串 `Flydigi VADER3`**
（VID_04B4 是 Cypress 的通用 VID），**产品名里根本就没有 "APEX 4" 字样**。
上游脚本按 `APEX[ _-]*4` 匹配产品名 → 同样会判 inconclusive。

**修法（相对上游的一次实质改进）**：
`VID_04B4&PID_2412` 是 APEX 4 **设备侧**的固有标识（真正有区分度的是 PID 2412），
实例 ID 命中它即可确认机型。修正后判定变为 `expected_model_reported`，
并把判定依据一并写进 `evidence`：

```
机型依据：实例 ID 命中 VID_04B4&PID_2412（APEX 4 固有标识；
产品名沿用旧固件字符串 "Flydigi VADER3"，不可作为判据）
```

### 3.4 上游诊断脚本在本机**必然**跑不通

上游 `Collect-Apex4-Diagnostics.ps1` 用 `Add-Type -TypeDefinition` 在运行时编译
XInput 探针（约 210 行内联 C#）。而**本机安全策略禁用 `Add-Type`**（README §5.8 已记录）
→ 该脚本在本机一定卡在 XInput 环节。

**修法**：整个收集器用 C# 原生重写，`DllImport` 直接绑定 `xinput1_4.dll` ——
反而比"运行时编译"更短、更快、无依赖。

### 3.5 `Win32_PnPEntity` 没有 ContainerID 属性

上游依赖 `Get-PnpDeviceProperty -KeyName DEVPKEY_Device_ContainerId`（CIM cmdlet，C# 无等价物）。

**修法（实测可行）**：容器 ID 就在注册表
`HKLM\SYSTEM\CurrentControlSet\Enum\<实例ID>\ContainerID`，**普通用户可读**。
实测 APEX 4 的 6 个实例返回同一个容器 GUID，聚类有效。

### 3.6 `FileInfo` 没有 `VersionInfo` 属性

那是 PowerShell 的 `Get-Item` 对象才有的。C# 要用 `FileVersionInfo.GetVersionInfo(path)`。

### 3.7 snake_case 策略会把 `XInput...` 拆成 `x_input_...`

`JsonNamingPolicy.SnakeCaseLower` 对 `XInputAvailable` 产出 `x_input_available`，
而上游脚本产出的是 `xinput_available`。字段名不一致会让两边报告没法直接对照。

**修法**：对该字段显式加 `[JsonPropertyName("xinput_available")]`。

### 3.8 报告里的步骤清单要与实际动作自洽

第一版在 `[6/7] 生成报告` 时就写 `summary.json`，`archive` 步骤之后才 `Add` →
**ZIP 存在，但报告里只列了 5 步**，自相矛盾。

**修法**：先记 `archive` 步骤、写好 `summary.json`，**再**创建 ZIP。

### 3.9 自检断言别按"引擎命令总数"写

第一版把断言写成 `catalog.Count >= 19`，但本页只收编**面向用户的 14 条**；
引擎另有 `bridge-triggers`（会话管理器专职）、`hidhide-watchdog`（内部看门狗）、
`help` 等。首跑因此误报"未通过"。

**修法**：改为按**命令 id 白名单**断言，并注明 14 条的来由。

## 5. 设计说明

### 5.1 为什么把命令元数据集中成一张表

19 个命令的参数散布在 `CliApplication.cpp` 的分发与各 `commandXxx()` 的解析循环里。
C++ 侧对未知选项的处理并不一致（有的 `return 1`，有的静默忽略），
因此"参数拼错"最可能的后果是**点了没反应**，而不是报错。

集中后，参数字母表与顺序只有 `EngineCommandCatalog.BuildArguments` 一处可改，
界面完全不需要知道引擎的参数细节。

### 5.2 三段式风险分区

硬件测试页按**影响等级**分三段，且在视觉上分隔（边框色：默认 → 警告色 → 错误色）：

| 分区 | 内容 | 可用条件 |
|---|---|---|
| 只读检测 | `diagnose` / `xinput-status` / `dry-run` / `virtual-ds` | 随时 |
| 硬件测试 | `test-rt` / `test-rumble` / `apex4-port-test` / `test-profile-switch` | 引擎在位 **且** 无会话 |
| 应急操作 | `clear` / `stop-active-sessions` / `restore-controller-visibility` | 随时；后两项**二次确认** |

`sessions` 运行期间，测试区**禁用按钮并显示原因**，而不是让按钮静默失败。

### 5.3 为什么诊断收集必须 C# 重写

三条理由，任何一条都足以构成重写：

1. 本机禁用 `Add-Type` → 原脚本必然在 XInput 环节失败；
2. 原脚本要求用户环境有 PowerShell + CIM cmdlet，而 DIA 是自包含 GUI 程序；
3. 原脚本的 README 面向英文社区，DIA 需要中文报告。

**保留了什么**：7 步流程、三级降级链（WMI → pnputil → reg query）、
JSON 字段名、"机型 / 连接模式"判定规则（APEX 4 在 XInput 模式下伪装成 `045E:028E` 的陷阱）。
