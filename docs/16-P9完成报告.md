## 5. 本次新踩的三个坑（值得写进通用清单）

### 5.1 SDK 风格 csproj 在 net462 下**静默跳过 XAML 编译**（最危险）

`<Project Sdk="Microsoft.NET.Sdk">` + `<UseWPF>true</UseWPF>` + `net462` 会**编译成功、0 警告 0 错误**，
但 XAML 根本没被编译：产物里没有 `<Assembly>.g.resources`，`InitializeComponent()` 到了
运行时才炸。第一次探针实测产物只有 6.6 KB、`grep baml` 为 0 —— 这就是发现路径。

- 根因：`Page` 通配与 WinFX 目标的开关 `_EnableWindowsDesktopGlobbing` 只在
  `Microsoft.NET.Sdk.WindowsDesktop` 管线里生效；纯 `Microsoft.NET.Sdk` 下 `UseWPF` 被忽略。
- 解法：显式用 `<Project Sdk="Microsoft.NET.Sdk.WindowsDesktop">`。
  实测同工程下 `obj/…/Xxx.baml` + `Xxx.g.cs` 生成、产物含 `DsInApex.Playnite.g.resources`。
- **守门**：`verify-p9.ps1` S1 有一条专门断言「g.resources 存在」—— 这个失败模式太安静，必须机器守。

### 5.2 PS 5.1 的 `Get-Content -Raw` 默认按 GBK 读无 BOM 的 UTF-8

S4 本地化审计首轮报「zh 缺 39 条 / 占位符不一致」，看着像翻译漏了一大半，
实际是**读取编码的锅**：GBK 解码会把中文字符后紧邻的 ASCII 字节（`</sys:String>` 的 `<`）
当成双字节字符的第二字节吃掉 → 正则大面积失配、键值错位。

- 解法：所有对无 BOM UTF-8 文本的读取显式加 `-Encoding UTF8`。
- 与既有结论（README §5.15）是同一族问题：**PS 5.1 与 UTF-8 的默认假设永远不可信**。

### 5.3 `-LiteralPath` + `-Include` 在 PS 5.1 下失效

`Get-ChildItem -LiteralPath <dir> -Recurse -Include "*.cs"` 的 `-Include` 会被忽略，
连 `bin` 这种**目录**都会作为结果返回，随后当文件读直接 `PermissionDenied`。

- 解法：`Get-ChildItem -Path (Join-Path $dir "*") -Recurse -File` + 在 `Where-Object` 里按扩展名过滤。

### 5.4 本机沙箱把 `MSBuild.exe` 列为 LOLBin，构建通道必须是 `dotnet`

`MSBuild.exe`（连同 `vswhere.exe`、`dotnet msbuild`）在本会话被安全策略直接拦。
所以插件构建**不能**沿用上游的 `msbuild <csproj>` 路子，只能走 `dotnet build`。
这反过来决定了 §5.1 的工程形态选择 —— 两者是绑定的。

### 5.5 环境缺口：本机无 .NET Framework 参考程序集，也没装 Playnite

- 参考程序集：`C:\Program Files (x86)\Reference Assemblies\…\.NETFramework\` **不存在**。
  解法：csproj 引 `Microsoft.NETFramework.ReferenceAssemblies`（NuGet 版），
  干净机器不必装 VS 的 targeting pack。
- Playnite 未安装 → SDK 由 `build-playnite-extension.ps1` 从 NuGet 取**钉版 6.16.0**
  并做 SHA-256 校验（`B83C0553…FF24`，与上游脚本记录的哈希逐位一致）。
  该包 `lib/` 下**只有 net462** —— 这就是插件 TFM 不能是别的的根本原因。

| 4 | 真实游戏起停（唯一硬尺子） | 手柄 DInput 模式 → 从 Playnite 启动受支持游戏 → 桥接被拉起、游戏正常 → 退出游戏后跑 DIA 自检，`tray_bridge.log` 须满足 `apex_original_restored=yes` |
| 5 | 与主程序互斥 | 先在 DIA 里起一个会话，再从 Playnite 启动游戏 → **游戏启动应被取消**并提示「另一个程序正在占用桥接」；反向（Playnite 先起）时 DIA 侧应拒绝起第二个会话 |
| 6 | 更新提示 | 点「检查更新」应报「已是最新版本（v0.7.0）」；把 `version.json` 临时改成低版本可模拟「发现新版本」→ 通知点击后弹确认框、确认后打开发布页 |

**环境不可复现项**：Playnite 全屏模式下的菜单行为（本机无 Playnite，桌面模式同样未验）。

## 7. 已知取舍与后续

1. **插件 Id 前缀从 `ApexSenseBridge_` 改为 `DsInApex_`**（GUID 沿用）。
   Playnite 按扩展 Id 分目录存配置，因此**旧版 0.6.x 的插件配置不会自动继承**。
   本次是首次交付、无历史用户，判定可接受；若日后要迁移，需加读取旧目录的兼容分支。
2. **`.pext` 未打进便携包**。`make-portable.ps1` 的产物布局被 `verify-p8.ps1` 的 S1
   当作基线（13 项布局 + 10 个 `*.xbf`），擅自加文件会让 P8 回归变红。
   建议作为独立议题：先在 `verify-p8.ps1` S1 里承认新增项，再让打包脚本带入 `.pext`。
3. **未做中文以外的语言**。只配 `en_US`（基底）+ `zh_CN`；其它语言的 Playnite 用户
   会回退到英文基底（`Loc` 的显式回退保证不会出现空白串）。
4. **版本号仍为 0.7.0**。P9 是开发阶段成果，`version.json` 未动；
   下次发版时再把 `.pext` 作为 Release 资产附上。
5. **插件工程**刻意**不加入 `DsInApex.sln`**。它 TFM 是 net462、依赖 `PlayniteSdkPath`
   与 Playnite SDK，塞进解决方案会让「直接 `dotnet build DsInApex.sln`」这条路在没有 SDK 的
   机器上直接失败。它由 `build/build-playnite-extension.ps1` 独立构建 —— 与主程序解耦是**有意的**。
