## 3. 过程中抓出并修复的两个真实问题

### 3.1 `ReadActual` 漏 InfoBar 分支（审计工具自身盲区）

`Localize.ApplyAuto`（写值）一直有 `InfoBar → Message` 分支，文案设置是好的；
但读值侧 `DumpApplied`（乃至新的 `ReadActual`）从来没有 InfoBar case ——
首轮审计把 13 处健康的 InfoBar 全部误报成「文案被丢弃」。

**教训（已写成注释钉在代码里）**：`ReadActual` 的读值 switch 必须与
`ApplyAuto` 的写值 switch **同构**，漏一个 case 就会产生系统性误报。
修复后 13 处哨兵全部消失（0 真缺陷）。

### 3.2 只读 ACL 下进程崩溃 —— WindowsAppSDK 引擎层硬行为（记录，非缺陷）

S4 用 `icacls /deny (W)` 模拟只读目录，进程在 `Program.Main` 的
Application initialization callback 阶段抛 `COMException 0x80040111`
（CLASS_E_CLASSNOTAVAILABLE）退出，早于任何 DIA 代码（自检日志零输出）。

根因链：NTFS 里目录的 `WD` 权限位 = add file —— deny(W) **必然**挡掉
「创建新文件」，而 WindowsAppSDK 的 XAML 引擎初始化需要在 app 目录建东西。
**本机无法用 ACL 模拟「只读但可跑」的真实介质**；U 盘物理写保护 /
CDFS 的失败语义与此不同，待真机 U 盘实测（人工清单 §5）。
因此 S4 定性为**信息性记录**，不阻塞验收。

> 顺带修掉的脚本层问题：`attrib +R` 对「在目录里创建新文件」无效
> （DOS 语义残留），第一轮 S4 曾因此误判「只读已生效」。

### 3.3 脚本被中途打断 → 自启项留成死链（已加固）

**现象**：首轮验收被用户取消（强杀）后，`HKCU\...\Run` 的 `DsInApex` 值被永久留在
`%TEMP%\DsInApex-P8\...\DsInApex.exe --autostart` —— 而该临时目录随后被删除，
注册表留下一条**指向不存在文件的死链**（开机静默失败，用户只会觉得"自启坏了"）。

**根因**：S3 需要改写自启项，收尾代码负责还原；但脚本被 Ctrl+C / 强杀时
**收尾代码根本不执行**。`finally` 也救不了进程被杀的情况。

**加固做法**（`verify-p8.ps1`）：
1. 开跑前把原值落盘成**恢复标记** `%TEMP%\DsInApex-P8-runbackup.txt`
   （格式含 `EXISTS=` 与 `VALUE=`，能区分「本来就没有」与「值丢了」）
2. 正常走完 → 摘除标记
3. 下次启动若发现标记仍在 → **说明上次异常中止** → 先按标记恢复再继续

**验证**：加固后完整重跑，6/6 全绿，且 `before -eq after` 为 True、
恢复标记已摘除（`docs/15` 记录本次实测）。

> **通则**：验收脚本凡要改系统状态（注册表 / 服务 / 文件关联），
> 都必须有「崩溃可恢复」的落盘标记，不能只靠末尾几行还原代码。

## 4. 验证方法学的两个定案

1. **自检跑完不退出是既有设计**（日志落盘后进程照常驻留 UI）。
   验收脚本的正确姿势是「轮询日志直到出现『自检结束』汇总行 → 杀进程读结果」，
   而不是 `WaitForExit` —— 后者只会白等到超时然后误报失败。
   这是 P5/P6 时代「跑固定时间 → 杀进程 → 读日志」取证方式的改进版。
2. **PS 5.1 脚本必须 UTF-8 with BOM**：Write 工具直出无 BOM 文件，
   PS 5.1 按 GBK 解析直接 ParserError。`build/make-portable.ps1` 当年是
   手工保存带 BOM 的；本次 `verify-p8.ps1` 首跑即踩，已用
   `[System.IO.File]::WriteAllText(path, text, UTF8Encoding($true))` 补上。
