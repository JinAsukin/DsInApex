### 2.1 段数说明

### 2.2 开机自启真机验证（路径漂移 → 自动纠偏 → 现场清理）

便携版的自启项存的是**绝对路径**，用户一旦挪动文件夹就会变成死链。
这条链路做了真机验证，分三步：

| 步骤 | 操作 | 结果 |
|---|---|---|
| 1 · 制造漂移 | 写入 `DsInApex = "D:\MovedAway\DsInApex.exe" --autostart`（一个不存在的路径） | 写入前确认该值**不存在**（干净起点） |
| 2 · 启动 DIA | 正常启动（`MainWindow` 构造里调 `AutoStartService.RepairIfStale()`） | 日志：`检测到自启路径漂移：登记值=""D:\MovedAway\…" → 自动纠正` → `已登记开机自启："…\win-x64\DsInApex.exe" --autostart`；自检显示 `自启状态 = Enabled`、`登记命令 = 本机命令`、**9/9 段通过** |
| 3 · 清理 | 删除注册表值 | `✓ 已清理：DsInApex 值不存在（与实验前一致）` |

关键设计：**只在 `StalePath` 时改写**。
「本来没开自启」的用户不会被悄悄打开 —— 那是越权，不是贴心。

## 3. 本轮踩到的坑（均已修复）

### 3.1 🔴 `MenuFlyoutItemBase` 上**没有** `Text` 属性 —— 而且我先猜错了两次

上游 `Localize.ApplyAuto` 的类型分派里只有 `case MenuFlyoutItem`。
P6 要在菜单里加子菜单/互斥项，于是先推理了两轮，**两轮都错**：

| 我的推理 | 事实 | 后果 |
|---|---|---|
| 「`MenuFlyoutSubItem` 继承 `MenuFlyoutItemBase`，而 `MenuFlyoutItem` 只匹配自己和子类」 | ✔ 推理正确 | 若不加分支，子菜单标题会掉进 `default` 被塞进 ToolTip → **菜单里一个空白项，编译期毫无提示** |
| 「那就改判共同的基类 `MenuFlyoutItemBase`，一次覆盖两种」 | ❌ **错**：`MenuFlyoutItemBase` 本身没有 `Text`（`CS1061` 编译器证实）。`Text` 是 `MenuFlyoutItem` 与 `MenuFlyoutSubItem` **各自声明**的 | 编译报错（这次幸好是编译期，不是运行期） |

**最终写法**：`MenuFlyoutSeparator`（无文案）→ `MenuFlyoutItem` → `MenuFlyoutSubItem` 三条分支分别写。

> 通则再次生效（README §5.12 那条）：**给没见过的控件加 `loc:Localize.Key` 前，
> 先确认它的正文属性叫什么**。这次是「先确认了它叫什么，但推断错了继承关系」，
> 教训升级为：**继承关系也要靠编译器确认，不要靠记忆推断。**

### 3.2 一片 `WMC0010` 再次由 **2 个** `error CS` 引发

构建输出里近 40 条 `Unknown attachable member 'Localize.Key'`（横跨 MainWindow、
Dashboard、Diagnostics、About 等所有页面），真正的根因只有两条：

```
Localize.cs(285,26): error CS1061: "MenuFlyoutItemBase"未包含"Text"的定义
Localize.cs(327,61): error CS1061: "MenuFlyoutItemBase"未包含"Text"的定义
MainWindow.xaml.cs(1228,13): error CS0246: 未能找到类型或命名空间名"ExitMeaning"
```

第二条：`ExitMeaning` 是 `EngineCommandCatalog` 的**嵌套** `readonly record struct`
（`EngineCommandCatalog.ExitMeaning`），不是顶层类型 —— 用 `var` 或全限定名即可。

修完这两条，40 条红字**一次全消**。README §5.3 的排查套路（只找 `error CS` → 撇开
`WMC0010` → 修根因）第三次救场，已足够固化为肌肉记忆。

### 3.3 `Microsoft.Win32.Registry` **不需要**显式引用（与 README 旧结论相反）

先前 README/`EngineLocator` 注释里写着「net10.0 下非内置，要显式引用」。
本轮按此加了 `<PackageReference Include="Microsoft.Win32.Registry" Version="5.0.0" />`，
编译器立刻报：

```
warning NU1510: PackageReference Microsoft.Win32.Registry 将不会删除。
               请考虑从依赖项中移除此包，因为可能不需要它。
```

这是 NuGet 的**包裁剪**提示：`net10.0-windows` 的框架里已自带注册表 API。
移除该包后 `Registry.CurrentUser` 照常编译，且构建回到 **0 警告**。

→ 已更正 README 中的旧结论。**同一条"必须显式引用"的教训对 `System.Management`
成立（缺了就编译不过），对 `Microsoft.Win32.Registry` 不成立** —— 两条不能互相类推。

### 3.4 「看门狗」根本不需要我造 —— 引擎早就全包了

P6 清单里写着「看门狗与恢复（沿用引擎 `hidhide-watchdog` 机制）」。
读引擎源码（`WindowsPhysicalControllerIsolation.cpp`）后才看清完整闭环：

1. 会话启动 → 写 HKCU `Software\ApexSenseBridge\PhysicalControllerIsolation` 快照
   （原白/黑名单、Phase、属主 PID、`ProfileRestorePending`、APEX 配置档等）；
2. 同时写 HKCU `...\CurrentVersion\RunOnce` 的
   `!ApexSenseBridgeRestoreControllerVisibility` → 保证下次登录兜底恢复；
3. 拉起 `hidhide-watchdog <pid> <token>` 子进程盯住属主，属主意外死亡即代为恢复；
4. 会话正常结束 → `clearRecoveryRegistration()` 把上面两处一起清掉。

**所以 DIA 该做的不是"再造一个看门狗"，而是"把引擎的状态讲给用户听"**：
只读这两处注册表 → 翻译成四种状态 → 发现 `PendingRecovery`（有标记、属主进程已死）
时提醒 + 给一个手动兜底按钮（仍调用引擎自己的 `restore-controller-visibility`）。

判活策略是**刻意保守的**：只认「PID 是否存活」，不校验镜像名。
PID 复用理论上会把「属主已死但 PID 被占用」误判成「会话进行中」——
但这只会让提示少一次；反方向误判会在用户正打游戏时弹出撤销提示，那才叫坏事。

### 3.5 便携版的「开机自启」必然遇到路径漂移

注册表存绝对路径 + 便携版可随意搬家 = 死链。
上游没有这个问题（它装到 `%ProgramFiles%` 且搬家不是正常用法），
**这是 portable 路线独有的坑**，因此必须显式建模成 `StalePath` 状态，
并在启动时自动纠偏（§2.2 已实测）。

## 4. 计划修订：P7 由「Inno Setup 安装器」改为 **portable 绿色版**

> 指令来源：本轮任务要求「软件开发成 portable 版本即可」。

### 4.1 改了什么

| 项 | 原计划（P7） | 修订后 |
|---|---|---|
| 交付形态 | Inno Setup 6 安装器（`.exe`） | **portable 绿色包**（`.zip`，解压即用） |
| 安装路径 | `%ProgramFiles%\Ds in Apex\` | 用户自选任意目录 |
| 注册表安装项 | 有（`SOFTWARE\ApexSenseBridge`） | **无** |
| 简体中文语言包 | 需集成社区 `.isl` | 不需要（无安装界面） |
| 卸载 | Inno 卸载器（保留 USBip 不自动卸） | **删除目录**（用户数据目录另行说明） |
| 开机自启 | 安装期写注册表 | **运行时由用户在设置页/托盘勾选**（HKCU `Run`，P6 已实现） |
| UAC / 提权 | 安装器提权 | 仅驱动安装时提权（P4 辅助模式，已有） |
| 升级方式 | 覆盖安装 | 下载新目录替换（用户数据与设置在 `%LOCALAPPDATA%` 不受影响） |
| 合规交付 | 安装器内嵌 LICENSE | **随包文件**：`LICENSE` / `THIRD_PARTY_NOTICES.md` / `SOURCE_OFFER.md`（P6 已落地并进输出目录） |

### 4.2 为什么这不是「少做一点」

去掉安装器**不等于**工作量变少，而是把责任从「安装器脚本」搬进了「程序自己」：

| 原本由安装器承担 | 现在由谁承担 | P6 状态 |
|---|---|---|
| 文件完整性校验 | `PortableLayoutService` 自查（引擎/安装器/许可证） | ✅ 已实现并进自检 |
| 许可证随包投放 | csproj 复制到输出目录 | ✅ 已实现 |
| 开机自启注册 | `AutoStartService`（含路径漂移纠偏） | ✅ 已实现并真机验证 |
| 卸载时的会话清理 | `ShutdownCleanup`（停会话 + 销毁托盘图标） | ✅ 已实现（P6） |
| 卸载时的控制器可见性恢复 | 引擎的 `RunOnce` 兜底 + 手动恢复入口 | ✅ 引擎机制 + P6 呈现 |
| 版本信息 / 图标 | csproj `Version` + `ApplicationIcon` | ✅ 已实现（0.7.0） |

**结论：P7 剩余工作收缩为「打包脚本 + 目录规范 + 发布流程」**，
但「安装器的活」已经有相当一部分在 P6 里落到了代码与合规物上。

### 4.3 对后续阶段的影响

- **P7**：改写为 `build/make-portable.ps1`（或 `.sh`）+ 目录结构规范
  （`DsInApex.exe` / `engine/` / `Prerequisites/` / 三个合规文件）+ 版本号对齐 + ZIP 产出。
  不再需要 Inno Setup 6 / 简中 `.isl`（环境准备清单可删两项）。

  「沿插件目录/配置路径向上找 `DsInApex.exe`」。**这是 P9 的一处新增工作量**，已记入待办。
  （P6 未动 Playnite 代码，属 P9 范围。）

## 6. 设计说明

### 6.1 为什么开机自启**不**写进 `tray_settings.json`

注册表 `Run` 键是唯一真源。若再在 json 里存一份，
用户手工删掉注册表项后设置页会显示「已开启」而实际没开 ——
**双真值是最难查的一类 bug**。因此界面每次显示都回读注册表（`Query()`），
写完也立刻回读（`Enable` → `Query`），保证「界面状态 = 系统状态」。

### 6.2 为什么恢复状态只读、不自动「修复」

因为**权威实现只有一个**（引擎）。DIA 若自己写一遍「撤销手柄隐藏」的逻辑，
就会有两个恢复器竞争同一份 HidHide 配置 —— 而引擎里还蹲着一个 `hidhide-watchdog`
子进程。所以 DIA 只做三件事：读状态、翻译给人看、把用户的恢复意愿转成引擎命令。

### 6.3 通知开关判断为什么收在一处

上游 WPF 版在每个订阅点都写了一遍 `if (settings.EnableNotifications)`，
漏一处就会出现「明明关了通知还在弹」。P6 把它收敛为
`NotificationService.NotifyIfEnabled(enabled, …)` ——
开关判断不再散落在各事件处理器里。

### 6.4 `--autostart` 为什么「先建窗口再藏」

WinUI 3 的窗口在首次 `Activate()` 之前，Mica backdrop / 标题栏 / DispatcherQueue 绑定
并未真正就绪，托盘与后续导航可能踩到空引用。
「完整初始化 → 立刻隐藏」是唯一稳妥的顺序，代价只是启动瞬间一次极短的窗口闪现。

## 7. 复现命令

```bash
# ── 构建（务必在代码区，先清理常驻托盘） ──
```
